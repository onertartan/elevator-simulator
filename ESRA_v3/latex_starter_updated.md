\begin{abstract}
Reproducible evaluation of elevator dispatching algorithms benefits from test scenarios whose construction and search difficulty are explicitly characterized. This paper presents ESRA v3, a Python-based extension of the Elevator Simulation, Research and Analysis framework, centered on difficulty-aware static scenario generation, visualization, and experiment management. Within a supported family of reference scenarios, the workflow varies spatial configurations while preserving selected aggregate characteristics. An exact subset dynamic programming solver computes a reference optimum for a static, unlimited-capacity destination-control assignment model that minimizes estimated mean passenger waiting time. Candidates are selected using the empirical proportion of random-restart, coordinate-wise hill-climbing runs attaining this optimum within a specified numerical tolerance and search budget. An optional preliminary screening stage uses a batch-best heuristic reference, which is kept distinct from the exact reference used for selection. The resulting difficulty indicator is objective- and protocol-dependent; exactness applies to the defined assignment model, not to subsequent dynamic simulation. A graphical interface exposes scenario-generation settings, while file-based static diagrams depict elevator states and passenger origin--destination relationships. The simulation display additionally visualizes waiting, boarding, and alighting passengers. A dedicated genetic algorithm parameter-search interface records configurations, random-seed settings, preserved input snapshots, per-run results, and statistical summaries. Together, these facilities support a scenario-centered workflow for controlled instance generation, exact-reference difficulty characterization, visual inspection, and repeatable optimization experiments.
\end{abstract}

Elevator dispatching, Exact optimization, Scenario generation, Search difficulty.

\section{Introduction}

Elevator group control involves assigning passenger requests to elevator cars while accounting for their positions, directions, and existing service commitments. Simulation provides a controlled environment for investigating these decisions and comparing alternative dispatching strategies. However, meaningful comparison requires more than executing different algorithms under identical conditions: the test scenarios themselves must also be characterized. Scenarios with the same numbers of floors, cars, and passenger requests can present different optimization challenges because the spatial arrangement of requests and the initial states of the cars affect the consequences of each assignment. This motivates an experimental workflow in which scenario construction, difficulty characterization, and performance evaluation are explicitly connected.

Our previous work introduced ESRA, an open-source, MATLAB-based framework for elevator traffic simulation, visualization, and controller development. Its modular architecture and support for saving and reusing traffic data provided a foundation for comparative studies \cite{tartan2024esra}. ESRA 2.0 extended this foundation towards configurable metaheuristic optimization and custom initial conditions supporting one-shot dispatch experiments \cite{tartan2025esra2}. These capabilities enabled researchers to configure optimization methods and reproduce operating conditions. The present work addresses a complementary question: how can controlled static scenarios be generated and selected according to an explicit, reproducible measure of search difficulty?

A distinction is necessary between traffic intensity and optimization difficulty. Increasing passenger demand changes the service workload, but does not by itself specify how difficult it is for a search procedure to find a high-quality assignment. Likewise, manually selecting initial conditions provides experimental control without establishing whether the resulting instances represent different levels of search difficulty. Here, a static scenario denotes a fixed decision snapshot containing elevator states, committed destinations, and outstanding passenger requests. It defines an assignment problem at a particular instant, rather than a complete dynamic traffic process. Such snapshots allow the optimization problem to be investigated separately from subsequent passenger arrivals and repeated dispatch decisions.

ESRA v3 generates candidate snapshots by varying car locations, movement directions, committed destinations, and passenger origin--destination configurations. Selected structural characteristics of a supported reference instance are preserved, including floor and car counts, directional passenger and hall-call counts, the total number of committed car destinations, and the number of upward-moving cars. The mean passenger trip distance is also constrained relative to that of the reference. The current generator targets a restricted family of moving-car snapshots, rather than every valid custom-initials configuration. Preserving these characteristics controls aspects of problem size and workload; it does not, by itself, imply equal optimization difficulty.

The difficulty-evaluation model assigns each floor--direction call, including all passengers associated with that call, to one car. Its fixed objective is the Python destination-control waiting-time function, which estimates the mean waiting time over passengers rather than an unweighted mean over calls. For a static snapshot, this estimate covers the time from the decision instant until pickup door opening begins; the pickup door-opening duration is not added. Assignments are evaluated under unlimited capacity and the route policy encoded in the objective. A subset dynamic programming solver computes an exact reference optimum for this defined assignment space. This optimum is not a claim of optimality for capacity-constrained operation or for the subsequent dynamic simulation.

Following an optional batch-best screening stage, each candidate proceeding to selection is evaluated against its exact reference optimum using random-restart, coordinate-wise hill climbing. The operational difficulty indicator is the fraction of runs whose final objective values match the optimum within a specified numerical tolerance. Candidate selection targets a user-defined interval of this success rate; lower rates indicate greater difficulty for the specified search procedure and budget. The current default selection budget is 1,000 random starts, with at most 100 full coordinate sweeps per start and early termination when a complete sweep finds no improving move. The batch-best value used in preliminary screening is not substituted for the exact reference: if the exact solve cannot be completed within the configured resource limits, the generation request terminates without accepting a candidate.

Although the reference optimum is obtained by an exact algorithm, the attainment rate remains an empirical, protocol-dependent estimate. It depends on the objective, initialization distribution, search rules, numerical tolerances, and stopping budget, and does not establish an algorithm-independent ranking of difficulty. Furthermore, a rate used to select a scenario should not also be presented as an independent validation of that selection. The implementation separates screening and selection random-number streams and reserves a distinct seed for later holdout evaluation. Such reassessment is a separate step, not an automatic outcome of scenario generation. Whether the resulting criterion supports stable and informative scenario selection remains the central empirical question.

The workflow is supported by complementary visualization and experiment-management facilities. A graphical scenario-generation interface exposes the reference instance, target success-rate interval, search budgets, and exact-solver limits. Static diagrams generated from scenario files depict car states and passenger origin--destination relationships, while the simulation display makes waiting, boarding, and alighting phases visible. These representations support inspection of generated inputs and their subsequent execution without equating the static objective with every detail of simulated passenger movement. A separate genetic algorithm parameter-search interface supports repeated fixed-snapshot experiments with recorded settings and seeds, preserved input snapshots, per-run objective values, and combination-level summaries reporting the mean, sample standard deviation, and best and worst results. The exact solver is also available through an interface-integrated dispatcher for the same destination-control objective.

This paper presents three connected contributions: a reference-based procedure for generating static dispatch scenarios and selecting candidates through an exact-reference, objective- and budget-dependent local-search attainment measure; a Python-based implementation of ESRA with explicit passenger-transition modeling and visualization; and complementary facilities for inspecting scenario inputs and managing repeatable optimization experiments. The scenario-generation procedure constitutes the central methodological contribution, while the implementation and experimental tools support its application and inspection. The contribution is the explicit use of a model-specific optimum to anchor empirical scenario selection, not a universal difficulty scale. Claims about the stability of this selection criterion require independent evaluation, while broader claims about dynamic traffic performance and computational speed require separate experiments.
